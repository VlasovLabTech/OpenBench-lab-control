# Micsig ETO5004 live test — 2026-08-03

## Hardware and network

- Instrument: Micsig ETO5004, four-channel 500 MHz oscilloscope.
- Serial number: `ETO-DEMO-0001`.
- Firmware: `3.392.132`.
- Hardware revision: not exposed by the instrument's `*IDN?` reply.
- Network adapter: integrated Wi-Fi, connected to the `Skoltech` enterprise
  WLAN.
- Address during this test: `198.51.100.28/24`; gateway `198.51.100.1`.
- Device MAC: `02:00:00:00:00:01`.
- Reachable services: TCP 80 (HTTP), 111 (portmapper), 5025 (SCPI), and 8888
  (screen stream).
- OpenBench device ID: `micsig_eto5004_ETO-DEMO-0001`. The ID is derived from the
  instrument serial and does not depend on the temporary IP address.

The protocol reference was Micsig's official
`Micsig-Oscilloscope-SCPI-Command-Manual-EN-202601`. It explicitly covers the
ETO family and documents LAN/Wi-Fi SCPI, standard waveform `DATA?`, ASCII/WORD
formats, and `:SYS:SCR?`. OpenBench used only bounded API operations; no raw
SCPI console or vendor driver was used.

## Safe bench state

This is a read/acquisition-only driver and cannot energize a source. No signal
generator or power-supply output was changed during the test. Existing analog
channel settings were preserved: all four channels displayed, 10x probes,
1 MOhm inputs, 1 V/div, and the pre-existing vertical positions. CH1 had no
test stimulus, so its captured samples and scalar amplitude/frequency were
expected to be zero or unavailable. Acquisition was restored to continuous
`RUN` after each frame attempt.

## API procedure and results

All actions went through `http://127.0.0.1:8000/api/v1` using the tracked
`skills/openbench/scripts/openbench_api.py` helper or the bounded screenshot
probe endpoint.

1. `health` returned `status: ok` and `safety_state: safe`.
2. `discover micsig_eto` found exactly one device and validated
   `Micsig,ETO5004,ETO-DEMO-0001,3.392.132`.
3. `scope-get micsig_eto5004_ETO-DEMO-0001` read acquisition, memory, timebase,
   CH1-CH4, EDGE trigger, and waveform state. Representative values were
   1.5 GS/s, 36 Mpoints, 2 ms/div, and trigger status `RUN`.
4. Scalar CH1 amplitude/frequency reads completed safely and reported
   unavailable values because no signal was connected.
5. A numeric CH1 capture used the documented transaction: STOP; source CH1;
   mode NORMAL; format ASCII; start 1; stop 1100; `DATA?`; preamble; restore
   previous waveform settings; RUN. It returned exactly 1,100 points and wrote
   a 34,613-byte CSV.
6. A follow-up `scope-get` confirmed trigger status `RUN` and the restored
   waveform source/mode/format.

After that bounded live test, OpenBench added a dedicated MAXIMUM-mode export
for stopped acquisition memory. The official manual specifies that MAXIMUM
returns memory data only while stopped and limits an ASCII read to 15,625
points. Mocked driver/service tests validate chunking, progress, exclusive
ownership, reader-context restoration, and the absence of memory-depth and
acquisition-state writes. A full physical MAXIMUM export was deliberately not
started during this record: the instrument reported `RUN` and a current depth
of 36 Mpoints, and this action is intentionally operator-triggered only after
the operator places it in STOP.

## Observed protocol limits and gaps

- The standard ASCII block header reports a number of points rather than a byte
  count. The driver therefore reads and validates 1,100 complete numeric tokens
  with a hard byte limit, then closes that waveform connection so firmware
  padding cannot contaminate the next SCPI response.
- Although WORD is documented as two bytes per point, this firmware's returned
  block length was not an unambiguous IEEE byte count. Production capture uses
  the validated ASCII path instead.
- The manual restricts `DATA:{HEX|BIN|ASCII}?` fast transfer to 12-bit scopes.
  ETO5004 is 8-bit, so OpenBench rejects its fast-binary diagnostic.
- Direct `:SYS:SCR?` produced no payload over raw TCP. The bounded VXI-11 probe
  ended with EOF and zero bytes after about 10.1 seconds. Screenshot capture is
  therefore not advertised for this firmware. The port-8888 H.264 screen stream
  and stored-file screenshot workflow were not promoted to production because
  neither has a pinned, validated, artifact-free still-image path.
- Channel/timebase/trigger setters share the documented bounded Micsig command
  surface and have mocked read-back coverage. Beyond the internal waveform
  source/mode/format/start/stop restoration used above, front-panel setting
  changes were not exercised on this unit during this test.

Result: physical discovery, stable identity, state reads, scalar reads,
Run/Stop restoration, 1,100-point calibrated waveform capture, and numeric CSV
export are validated on ETO5004 firmware `3.392.132`. The separate STOP-only
MAXIMUM full-memory path has automated contract coverage but has not yet been
claimed as a completed 36-Mpoint physical transfer.

## Follow-up live test — 2026-08-13

The same serial and firmware were retested at `203.0.113.12` through the public
OpenBench API. The front panel was visibly in ordinary Y-T/Normal mode although
`:TIMebase:MODE?` returned `XY`; the ETO-only firmware profile now normalizes
that known-bad readback to `YT` without changing the scope.

The standard ASCII path remained extremely slow and intermittently returned a
zero block. Standard `FORMAT WORD` plus `DATA?` returned 1,100 samples encoded as
four ASCII hexadecimal characters per point. Its preamble reported twice the
physical vertical scale; comparison with the independent CH1 scalar measurement
(about 12.55 V) validated a firmware-specific 0.5 correction. A corrected CH1
trace contained 1,100 points spanning about 11.85–12.25 V. A second source in
the same stopped frame still returned an empty block after a fresh connection,
one bounded retry, and a one-second source settle. Atomic four-channel Data is
therefore not validated on this firmware.

Direct `:SYS:SCR?` remains unavailable, but the documented
`:STORage:CAPTure:STARt` workflow succeeded. OpenBench discovered and downloaded
the new file through `/pictures/Screenshots`; the live Snapshot completed in
about 1.64 seconds and saved a valid 188,406-byte 1920x1200 PNG as
`.openbench/data/captures/sessions/20260813_1724_snap_eto5004_sc/eto_screen.png`. The image
contains all four displayed traces and visibly reports `Normal`. Production ETO
Screen now uses this stored-file fallback. It leaves the generated image on the
scope because OpenBench does not use an undocumented or unreliable delete path.
