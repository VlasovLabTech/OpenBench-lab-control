# OpenBench: актуальный контекст проекта

Этот документ — короткий контекст для разработчиков и автоматизации. Он
описывает фактически реализованную систему на 24 августа 2026 года. Подробные
контракты находятся в документах, перечисленных в разделе «Источники истины».

## Назначение

VlasovLab OpenBench — локальное приложение для подключения лабораторных
приборов, просмотра измерений, безопасного ручного управления, записи CSV и
синхронизированных артефактов. Приложение рассчитано на инженерный стенд и по
умолчанию доступно только на `127.0.0.1`.

Пользователь работает через Dashboard. Автоматизация, включая Codex, работает
через ограниченный REST API. Прямые произвольные SCPI, serial, shell, GPIO и
команды обхода безопасности не являются частью публичного интерфейса.

## Что реализовано

- FastAPI-приложение, Jinja2/HTMX Dashboard, WebSocket live measurements и
  интерактивная OpenAPI-страница.
- Русский и английский интерфейс с переключателем языка; английский остаётся
  исходным техническим языком API и документации.
- SQLite для инвентаря, измерений, matrix profiles и безопасных настроек
  приборов.
- Общие snapshot и CSV recording с title/comment, широкими таблицами и
  относительными ссылками на артефакты.
- Коммутационная матрица с validate-before-apply, break-before-make,
  interlock и глобальным `ALL OUTPUTS OFF`.
- Безопасный локальный REST API и канонический Codex skill в
  `skills/openbench/`.

| Класс | Реализация | Статус |

| Тестовый источник | Simulated Meter / Matrix | CI и локальные тесты |

| Источник питания | FNIRSI DPS-150 | физически проверен |
| Source + DMM | OWON SPM6103 | физически проверен |
| Двунаправленный источник/нагрузка | ITECH IT6054C-800-225 | физически проверен |
| Логический анализатор | Kingst LA2016 через sigrok | физически проверен |

Точная модель, прошивка, ограничения и качество проверки описаны в датированных
записях `docs/*live-test*.md`. Серийные номера, MAC, локальные IP и номера COM в
публичной версии заменены демонстрационными значениями; это не меняет результаты
или командные контракты.

## Архитектура

```text
src/openbench/
├── api/         REST и WebSocket
├── core/        registry, scheduler, event bus, safety
├── domain/      неизменяемые доменные модели
├── drivers/     ограниченные транспорты и протоколы приборов
├── services/    управление, измерения и capture orchestration
├── storage/     SQLAlchemy и настройки по стабильному device ID
└── web/         Jinja2/HTMX интерфейс и статические файлы
```

Основные зависимости направлены от внешних интерфейсов к сервисам и доменной
модели. API и UI не должны обходить сервисы безопасности и обращаться к
физическим транспортам напрямую.

## Ключевые правила безопасности

1. Включение любого физического выхода требует явного действия оператора.
2. Для действий с энергией должны быть известны схема подключения и нагрузка.
3. Выключение выхода всегда считается безопасным действием.
4. При disconnect, shutdown и emergency stop поддержанные источники обязаны
   перейти в Output OFF; коммутационная матрица размыкается.
5. Пресеты могут изменить энергонезависимую память и восстановить включённые
   выходы, поэтому их save/load требует явного запроса.
6. ITECH Output ON требует `wiring_confirmed`, безопасную матрицу и включённые
   OVP/OCP/OPP. Положительный ток означает источник, отрицательный — нагрузку.
7. Максимальный ASCII-захват MHO1/ETO5004 запускается только в уже остановленном
   состоянии, не меняет depth и эксклюзивно владеет прибором до завершения.
8. Произвольные SCPI, serial, shell, GPIO и safety-bypass endpoints запрещены.

Полные правила находятся в `AGENTS.md`, `skills/openbench/SKILL.md` и
`docs/automation-api.md`.

## Опрос и данные

- Общий стандарт Dashboard — 1–2 Гц, но фактический минимум определяется
  драйвером и возвращается API.
- Scheduler не запускает два одновременных poll одного канала, использует
  monotonic time, timeout/cancellation и помечает stale/invalid данные.
- Waveform и logic data сохраняются как конечные capture artifacts, а не как
  поток REST-запросов.
- Контекст прибора, polling и безопасные предпочтения сохраняются по стабильному
  device ID. Переподключение не включает выход и не запускает захват.

## Локальные данные

Весь изменяемый runtime state хранится под игнорируемым каталогом `.openbench/`:

```text
.openbench/
├── data/
│   ├── openbench.db
│   └── captures/
├── tools/       воспроизводимо собираемые или устанавливаемые runtime tools
├── cache/       загрузки и кэши инструментов
├── audit/       локальные отчёты проверок публикации
└── archive/     старые локальные исследования и контекст
```

База, capture-комментарии и артефакты могут содержать чувствительные сведения о
стенде и не должны попадать в GitHub, issue или release. Обязательные скрипты,
patches, source pins, checksums, manifests и лицензии, напротив, должны быть в
Git: игнорируемая локальная папка не может быть единственным источником
воспроизводимости.

## Переносимость

- Проверенный пользовательский путь — Windows 10/11 и Python 3.11+.
- `Setup OpenBench.cmd` создаёт `.venv` из зафиксированного Windows lock-файла.
- `Start OpenBench.cmd` проверяет lock hash и выполняет setup при необходимости.
- Основной Python-слой тестируется CI на Windows и Linux; физическое Linux-
  оборудование остаётся experimental до отдельных live-test records.
- Dashboard не использует CDN: HTMX и его лицензия находятся в репозитории.
- Kingst firmware извлекается из закреплённого официального пакета локально;
  проприетарная прошивка не публикуется.
- Windows sigrok runtime собирается из закреплённых исходников с tracked patch,
  manifest, checksums и third-party licenses.

## Изменение проекта

- Сохранять обратную совместимость REST API и helper в
  `skills/openbench/scripts/openbench_api.py`.
- При изменении API или safety behavior одновременно обновлять
  `docs/automation-api.md`, `skills/openbench/SKILL.md` и компактную skill-
  reference.
- Новый физический драйвер должен следовать `docs/driver-development.md` и иметь
  датированную запись физической проверки.
- Любая новая строка интерфейса должна иметь русскую запись в
  `src/openbench/web/static/i18n.js`; безопасность и смысл единиц нельзя менять
  при переводе.
- Перед публикацией выполнять Ruff, mypy, pytest, clean-install smoke test и
  secret/privacy audit.

## Текущие ограничения

- Это локальный инженерный инструмент, а не удалённая многопользовательская
  система. Аутентификация и TLS не реализованы; не публикуйте порт наружу.
- Recipe engine, lease manager и произвольная пользовательская оркестрация не
  входят в текущий продукт.
- Linux hardware access и udev rules не прошли полную физическую матрицу.
- MHO1 maximum-memory path имеет mocked coverage до завершения отдельного
  стендового плана; ETO5004 STOP-gating проверен физически.
- Некоторые команды FeelElec не имеют read-back в опубликованном протоколе и
  явно помечаются как unverified.

## Источники истины

При расхождении использовать документы в таком порядке:

1. код, тесты и живой `/openapi.json`;
2. `AGENTS.md` — обязательные правила работы в репозитории;
3. `docs/automation-api.md` — полный API и safety contract;
4. `skills/openbench/SKILL.md` и его compact reference/helper;
5. `docs/architecture.md` — структура реализации;
6. `docs/portability.md` и `docs/driver-development.md`;
7. этот обзорный контекст.

Старый стартовый промпт и первоначальный длинный концепт сохранены только в
локальном `.openbench/archive/context/` и не входят в публичный репозиторий.
